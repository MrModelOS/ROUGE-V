# ADR-0006: AOT-компилятор на LLVM/MLIR — основной путь выполнения CUDA-кода

- **Статус:** Принято
- **Дата:** 2026-09-20
- **Владелец:** архитектор компилятора (возможный скептик: архитектор runtime)
- **Отменяет/изменяет:** развивает ADR-0005 (место статической трансляции внутри гибрида)

## Контекст

ADR-0005 зафиксировал гибридный CUDA-совместимый слой: динамический перехват
(ZLUDA-подход) + будущая статическая трансляция. В `software/rouge-cuda`
работает первый компонент — интерпретатор PTX на CPU и перехват символов
libcuda/libcudart. Интерпретация инструкция-за-инструкцией честна, но это
**не** тот путь, на котором мы догоняем NVIDIA по производительности:
на одном ядре CPU с эмуляцией мы никогда не получим GPU-пропускную
способность.

Параллельно: индустрия двигается к открытым промежуточным представлениям
(Triton, MLIR GPU-диалекты, UXL/SYCL). NVIDIA сама компилирует `.cu` через NVVM
IR (LLVM) в PTX — то есть у нас есть стандартизированная точка перехвата:
**готовый LLVM IR / PTX**, которые не нужно парсить с нуля.

## Варианты

1. **Остаться на интерпретаторе PTX** — плюс: уже работает; минус: потолок
   производительности в десятки раз ниже нативного, масштабирование только
   вширь, на кремнии не применим.
2. **AOT-трансляция PTX/IR → нативный код через LLVM/MLIR (выбрано)** — плюс:
   нативные бинарники без эмуляции, единый конвейер для x86/ARM/RISC-V, путь к
   RVV-векторизации и собственному ISA ROUGE; минус: сложнее, требует LLVM-
   стек, поддержка подмножества PTX растёт постепенно.
3. **Только open-фронтенды (Triton/SYCL), без PTX** — плюс: чисто; минус:
   теряем рынок готовых CUDA-бинарников, который и даёт компет-слой смысл.

## Решение

Основной путь выполнения CUDA-кода — **AOT-компилятор** (репозиторий
`software/rouge-compiler`, архитектура: `docs/06-compiler-architecture.md`):

```
CUDA Source / NVVM IR / PTX
        │
        ▼
1. CUDA/PTX Parser (общий фронтенд rouge-ptx; NVVM IR Reader — LLVM)
        │
        ▼
2. MLIR Dialect Conversion (GPU/NVVM -> Vector/Linalg -> ROUGE Dialect)
        │
        ▼
3. Hardware-Aware Optimization Pass (Tiling, Memory Coalescing, Double Buffering)
        │
        ▼
4. RISC-V LLVM Backend (rv64gcv_xrouge) / нативный хост-код
        │
        ▼
Native ROUGE-V Binary + Runtime API (замена libcuda.so / libcudart.so)
```

Рабочая веха: `ptx2ir` транслирует PTX-подмножество в текстовый LLVM IR
(кернел vadd), clang компилирует его в нативный объект, хост-драйвер исполняет
и проверяет результат — **без эмуляции инструкций**. Тот же IR собирается
LLVM-бэкендом для `rv64gcv` (RISC-V + Vector), что проверяет целевой
бэкенд-путь.

Связь с интерпретатором: rouge-cuda остаётся **страховкой и fallback** —
для неподдерживаемых AOT-ом инструкций и для быстрых проверок; основной
перф-путь — нативный бинарник. Оба компонента разделяют общий PTX-фронтенд
`software/rouge-ptx`.

## Последствия

- **Софт:** растёт стек LLVM/MLIR; регрессионные тесты на нативные запуски
  (не только структурные); набор поддерживаемых инструкций расширяется
  по дорожной карте (shared, атомики, bar.sync, FP16/BF16).
- **Кремний:** компилятор целится в `rv64gcv_xrouge`; векторное ядро и
  MMA-расширения (ISA ROUGE) проектируются под конвейер MLIR, а не под
  интерпретатор.
- **Деньги:** AOT — единственный реалистичный путь к перф-паритету с
  NVIDIA-бинарниками («20 строк vLLM работают без перекомпиляции»);
  интерпретатор — только dev-инструмент.
- **Риски:** LLVM-зависимость (лицензия Apache 2.0 — ок), сложность MLIR —
  митигируется поэтапным вводом (сначала скалярный AOT, затем RVV-векторизация).

## Обратные сигналы (когда пересматривать)

- Если окажется, что перехват NVVM IR (вместо PTX) даёт кратно лучший
  результат — переключаем точку входа компилятора (фронтенд остаётся).
- Если индустрия откатится от PTX-совместимости — сокращаем приоритет
  PTX-пути, но не LLVM/MLIR-конвейера.
- Если RISC-V Vector окажется недостаточным для SIMT-маппинга — решение о
  собственных ISA-расширениях (Xrouge) становится критичным раньше плана.
