# ADR-0005: Архитектура CUDA-совместимого слоя

- **Статус:** Принято
- **Дата:** 2026-09-20
- **Владелец:** Архитектор ПО
- **Отменяет/изменяет:** конкретизирует ADR-0002 (open-standards-first, вариант 3)

## Контекст

Главный барьер миграции с NVIDIA — существующий код на CUDA (ядра на CUDA C/C++, PTX, вызовы runtime/driver API). Часть легаси не будет переписана годами. ADR-0002 зафиксировал: открытые стандарты — первичный путь, CUDA-совместимость — вторичный слой, без копирования кода NVIDIA (юридические риски: иски NVIDIA против совместимых слоёв).

Вопрос: какую форму принимает слой совместимости? Варианты:
1. **Статическая трансляция исходников CUDA → Triton/SYCL**: обещание «твой исходник собирается у нас». Плюс: нативный код, скорость, целостность. Минус: не покрывает бинарники и закрытый исходный код; тяжёлая инженерия.
2. **Динамический перехват (ZLUDA-подход)**: подменяем загрузку `libcuda`/`libcudart` нашей библиотекой, перехватываем driver/runtime API и PTX-ядра, исполняем своим бэкендом. Плюс: бинарная совместимость, легаси запускается без перекомпиляции. Минус: гонка за широтой API; PTX-джаст ставит потолок производительности.
3. **Гибрид (выбрано):** динамический перехват + PTX-интерпретация для легаси **и** статическая трансляция для тех, кто готов пересобрать (миграционный путь к нативным ядрам ROUGE).

## Решение

**Гибрид:** каркас динамического перехвата построен первым (`software/rouge-cuda`), поверх него развивается PTX-бэкенд; статический транслятор — второй трек (CUDA C → Triton → наш компилятор), включается после первого продакшен-релиза слоя.

Контрактные правила:
- Перехват **только через наши заголовки и реализацию**; никакого копирования кода NVIDIA или её заголовков.
- Каждый реализованный символ — это **обещание контракта**: список живёт в `include/rouge/cuda.h` и `cuda_runtime_api.h`.
- Если в системе загружена настоящая CUDA-библиотека — проброс (`dlsym`, RTLD_NEXT-семантика) в неё; иначе — собственная реализация (CPU-эмуляция → позже аппаратный бэкенд).
- PTX-покрытие растёт от набора реально используемых моделей (критерий отбора: канонические бенчмарки ROUGE-bench), а не «все опкоды подряд».
- Архитектурные ошибки слоя (неверный результат) фиксируются тестами до расширения набора инструкций.

Текущая реализация (v0): CPU-эмуляция, парсер PTX-подмножества, интерпретатор (см. `software/rouge-cuda/README.md`). Три теста зелёные: `driver_vadd` (PTX-ядро через Driver API), `runtime_api` (cudaMalloc/cudaMemcpy/streams), `interposer` (экспорт символов для LD_PRELOAD).

## Последствия

- Софт: слой живёт в `software/rouge-cuda`; расширение набора PTX-опкодов — через DR (тест сначала).
- Юристы: решение «без копирования» зафиксировано; аудит зависимостей при добавлении транслятора.
- Продукт: легаси CUDA безболезненно запускается (аргумент миграции), но маркетинговый девиз не выдвигает CUDA как основной путь.
- Риск: широта API окончательно не покрыта → метрика покрытия (сколько символов реальных приложений) добавляется в ROUGE-bench.

## Обратные сигналы (пересматривать, если)

- NVIDIA выигрывает суды против динамического перехвата → переносим акцент на статическую трансляцию (усиление Triton-пути).
- Реальные клиенты используют CUDA-бинарники чаще, чем ожидалось → увеличение приоритета PTX-бэкенда.
- PTX-бэкенд упирается в производительность (интерпретация) → пересмотр: прямой JIT в нативный код.
