# MLIR-контур ROUGE-V (стадия 2 конвейера: GPU → Vector → RVV)

Стадия 1 (`ptx2ir`: PTX → LLVM IR → нативный код) живёт в родительском каталоге
и собирается везде. Этот каталог — **стадия 2**: lowering SIMT-семантики в
векторные операции RVV через MLIR.

## Статус: контур собирается и проверяется

Что уже есть:

- `lib/Transforms/SimtAccessReport.cpp` — проход `--rouge-simt-access-report`:
  **анализ** SIMT-паттернов (thread/block id, барьеры, global/shared traffic,
  атомики, vector-операции) по функциям. Ничего не переписывает: его задача —
  сделать измеримым то, под что проектируется векторизатор (unit-stride
  участки между барьерами).
- `tools/rouge-opt/rouge-opt.cpp` — драйвер вроде `mlir-opt` с нашими проходами.
- `tools/rouge-compile/rouge-compile` — бэкенд-драйвер: PTX → диалект → петли
  → вектор → LLVM IR → ассемблер (`cpu`, `rvv`). Своей кодогенерации нет.
- `test/simt_access_report.mlir` — тестовый вход (GEMM-тайл + чистый copy);
  `test/simt_access_report_atomic.mlir` — атомики (синтаксис `atomic_rmw`
  изменился в MLIR 23, поэтому ячейка включается только на MLIR >= 23).

Проверено на MLIR 23.1.3 (официальный релиз LLVM, ровно та версия, что стоит
в системе): контур собирается, `rouge-opt` печатает отчёт по функциям, обе
ячейки ctest зелёные. Пример вывода:

```
rouge-simt-access-report: module '(anonymous)'
  scale_copy: loads=1 stores=1 vector=0 atomics=0 barriers=0 ids=0
  gemm_tile: loads=2 stores=2 vector=2 atomics=1 barriers=1 ids=2
rouge-simt-access-report: lowering plan hints
  scale_copy: unit-stride candidate — SIMT->RVV vectorizable
  gemm_tile: mixed access — vectorize only the runs between barriers
```

### SIMT -> SCF: проход написан и работает

Первый переписывающий проход (`lib/Transforms/SimtToScf.cpp`, `--rouge-simt-to-scf`)
переводит ядро в форму с явными циклами: `gpu.launch_func` -> цикл по сетке,
тело ядра разбивается на **фазы по барьерам**, `gpu.thread_id x` становится
индуктивной переменной, `gpu.block_id x` — аргументом ядра. Разбивка на фазы не
украшение: без неё поток 0 выполнил бы весь код после барьера раньше, чем поток 1
выполнит код до него, и смысл барьера потерялся бы.

Проверяется двумя ячейками: `mlir_simt_to_scf` (структура результата: две
фазы-цикла, запуск-цикл по сетке, `gpu.thread_id` исчез) и
`mlir_simt_to_scf_divergent` (ядро с расхождением обязано быть **отвергнуто**
громкой ошибкой, а не тихо переписано).

Что стоило выяснить по дороге (общие грабли для любых проходов, которые
переписывают тело функции):

1. **Тело `scf.for` в MLIR 23 строится отдельно.** Статический
   `scf::ForOp::create(...)` оставляет регион пустым, а и `OpBuilder::create`
   (устаревший), и `OpTy::create` требуют `ImplicitLocOpBuilder`, который
   нельзя построить из обычного `OpBuilder` (класс не копируется). Рабочий
   путь: собрать операцию через `OperationState`, тело создать руками и положить
   в регион. Взять `getBody()` у пустого региона — это вставка операций в
   мусор: в модуле остаётся уничтоженная операция, и падает потом верификатор,
   а не проход.
2. **Диалект должен быть ЗАГРУЖЕН, а не только зарегистрирован.** Вход без
   `scf`-операций не грузит SCF-диалект, и создание `scf.yield` падает с
   «created with unregistered dialect». Лечится `getOrLoadDialect<SCF>()`.
3. **Клоны обязаны перемапливать операнды — и в инвариантной части, и в
   фазе.** Клон, ссылающийся на оригинал, — это висячая ссылка (оригинал
   умирает вместе со старым ядром). Проявляется сильно позже и совсем в другом
   месте: в верификаторе, в `Type::getContext()`.
4. **Значения из launch-операции надо клонировать в новое ядро.** Размер блока —
   операнд `gpu.launch_func`, он определён в ХОСТ-функции, а новое ядро — её
   сестра, а не вложенный регион: значение не видно и повисает, когда launch
   стирается.
5. **Операции, не зависящие от thread id, надо выносить из цикла.** Иначе
   константа, определённая в первой фазе, не доминирует над использованием во
   второй. И сам `gpu.thread_id` — «зависимый» по определению: вынесенный
   наружу, он дал бы всем потокам одно значение.
6. **`index_cast` из index в index — невалидный IR.** Размеры сетки и блока в
   gpu-диалекте уже `index`, лить их в index наивно нельзя.
7. **Блок-id добавляется в вызов ядра только если ядро его принимает.** Иначе
   вызов получает лишний операнд не того типа (и верификатор падает на
   `arith.index_cast` с типом `memref<...>`).

### Свой диалект `rouge`: ядро в диалекте, который мы владеем

План 2.0 требует, чтобы ядро описывалось НЕ апстримным `gpu`-диалектом, а
своим. Диалект (`include/rouge/IR/RougeOps.td`, `lib/IR/RougeDialect.cpp`)
намеренно маленький — шесть операций, и всё, что не SIMT-специфично, остаётся
в стандартных диалектах:

```
rouge.thread_id / block_id / block_dim / grid_dim   идентичность и размеры
rouge.barrier                                        барьер между фазами
rouge.launch                                         запуск по сетке блоков
```

Арифметика остаётся в `arith`, обращения к памяти — в `memref`: переписывать
их означало бы переписывать вместе с ними и векторизатор. И адресное
пространство — часть типа memref (`memref<64xf32>` — глобальная память,
`memref<64xf32, 3>` — общая), поэтому «общая» и «глобальная» не путаются по
 построению, а CPU-lowering может превратить общую память в private-накопитель
одним типом.

Lowering написан ОДИН раз (`lib/Transforms/SimtToScfImpl.h`) и используется обоими
диалектами: у gpu-диалекта и у нашего различается только драйвер (у нас ядро —
обычная `func.func`, поэтому проход обходит ЗАПУСКИ и находит ядро по символу).
Две копии lowering означали бы два места, где чинится одна и та же тонкая ошибка.

Проверка, которая важнее всех остальных: одно и то же ядро, написанное в двух
диалектах, проходит одну и ту же цепочку (SIMT → SCF → Vector → LLVM IR →
ассемблер RISC-V → qemu-riscv64) и даёт одно и то же число (код возврата 96 в
обоих случаях). Наш диалект — ЗАМЕНА апстримному, а не переименование.

Ячейки: `mlir_rouge_to_scf` (структура), `mlir_rouge_to_scf_shared` (отказ по
общей памяти, приходящей параметром), `mlir_rouge_to_scf_shared_alloc` (общая
память, объявленная внутри ядра, — lowering), `mlir_rouge_shared_semantics`
(СЕМАНТИЧЕСКАЯ проверка: сумма обязана быть 96.000000), `mlir_rouge_to_rvv`
(полная цепочка с исполнением под qemu).

Грабли MLIR 23 (найдены дорогой):

1. **Атрибут диалекта надо ЗАРЕГИСТРИРОВАТЬ через `addAttributes<>()`** в
   `initialize()`. Без этого атрибут создаётся, а хранилище для него не
   инициализировано — и падение происходит в `getOrCreate`, то есть в
   РЕЛИЗНОЙ сборке падает (проверка «dialect was likely not loaded» — это
   `assert`, в release он вырезан).
2. **Перечисление требует `-gen-enum-decls/defs`, а атрибут —
   `-gen-attrdef-decls/defs`**, и объявления операций лежат в отдельном
   `.h.inc`; определения операций требуют макроса `GET_OP_CLASSES`.
3. **Диалект, собранный с RTTI, не линкуется с MLIR, собранным без RTTI**:
   vtable диалекта тянет typeinfo `mlir::Dialect`, которого в библиотеке нет.
   Диалект тоже надо собирать с `-fno-rtti`.
4. **`MemRefType::get` в MLIR 23: порядок аргументов — (shape, elementType,
   layout, memorySpace)**, память пространства идёт последней.

### Фронтенд: PTX -> диалект `rouge`

Диалект без входа — игрушка, поэтому PTX (тот самый текст, который даёт
nvcc) переводится в диалект: `rouge-ptx2mlir kernel.ptx -o kernel.mlir`.

**Модель памяти — главное решение здесь.** PTX оперирует ПЛОСКИМИ
указателями: параметр ядра — это u64, а арифметику адреса ядро делает само.
MLIR-овский memref СТРУКТУРИРОВАН: база, форма, шаг. Фронтенд восстанавливает
структуру из арифметики адресов:

```
cvta.to.global.u64 %base, %param;
mul.wide.u32 %off, %index, <размер элемента>;
add.s64 %addr, %base, %off;
ld.global.s32 %v, [%addr];
```

превращается в

```
%v = memref.load %param[%index] : memref<?xi32>
```

Восстановление намеренно узкое: база — только параметр ядра (или переменная
общей памяти), индекс — только масштабированный ровно на размер элемента, и
между ними ничего. Всё остальное **отвергается** с сообщением, что именно не
понято: ошибка здесь — это чтение не той памяти, а тихое угадывание — ровно то,
что проект не поставляет.

Размер (форма) массива в PTX отсутствует (GPU не знает про формы) — он
динамический по умолчанию и задаётся подсказкой (`--shape 0=64xi32`): форму
знает только вызывающий, а векторизатору нужна статическая.

Что переводится: идентификаторы (thread id, block id, размеры сетки и блока),
целочисленная и вещественная арифметика, сравнения, преобразования, обращения
к памяти, барьер, ранний выход (`@%p bra` в точку слияния -> `scf.if`),
`popc`/`clz`/`dp4a`, битовые поля (`bfi`, `bfe`, `prmt`). Остальное — отказ.

### Битовые поля: семантика по ISA, а не по догадке

`bfi`, `bfe` и `prmt` — это то, чем nvcc разбирает и собирает байты
(например, при понижении `__shfl_sync` и упаковке `char4`), поэтому они
нужны. Первая версия обеих реализаций (интерпретатор и AOT) понимала их
«по-своему»:

* `bfi` вставляла `b` в `a`, а не наоборот;
* позиция и длина читались из одного упакованного иммедиата
  (`pos | len << 8`), которого в PTX нет;
* `prmt` брал только младший ниббл селектора.

Интерпретатор и AOT при этом совпадали бит в бит — на неверном ответе.
Отсюда правило: тест битовых полей **трёхсторонний**. Одно и то же ядро
(`tests/kernels/bitfield.ptx`, 9 случаев на слово) считается

1. нативным кодом (`ptx2ir` + `clang` + запуск),
2. нашим интерпретатором PTX,
3. псевдокодом из PTX ISA (9.7.9 для `bfi`/`bfe`, 9.7.10 для `prmt`),
   переписанным в тесте независимо от первых двух.

Ячейка CI: `aot_native_bitfield`. Расхождение любой из трёх сторон — провал.
В частности, так был найден пропущенный `strtoull(..., 10)` для hex-иммедиатов
(`0x1f` молча читался как 0) — тихая ошибка в самом эталоне.

Во фронтенде позиция и длина `bfi`/`bfe` и селектор `prmt` обязаны быть
**константами**: от них зависят зажимы к границе слова и режим `prmt`
(биты 19:16 селектора), а динамическое значение нельзя проверить — только
угадать. Динамический операнд отвергается с сообщением, а не компилируется
в цепочку `select`, которая верна «в среднем». Режим `prmt` кроме нулевого
тоже отвергается.

Две детали, без которых векторизация не работает на настоящем выводе nvcc:

* **идентификатор потока остаётся идентификатором.** `mov.u32 %r, %tid.x`
  даёт `rouge.thread_id`, а не `index_cast`: индекс доступа сохраняет форму
  «поток + константа», которую узнаёт векторизатор;
* **мёртвые вычисления удаляются.** Фронтенд эмитит каждую инструкцию, в том
  числе регистры, которые ядро никогда не читает; в конце перевода чистые
  операции без использований удаляются (терминаторы и операции с побочными
  эффектами не трогаются). Иначе мёртвая цепочка `index_cast -> extui`
  попадает в тело цикла, и векторизатор отказывает из-за неё, а не из-за
  сути;
* **размер общей памяти считается по её объявлению.** `.b8 sdata[256]` — это
  256 **байт**, а memref считает в элементах того типа, которым ядро
  обращается: `memref<64xi32>`. Игнорирование этой разницы занижает размер,
  когда объявление крупнее доступа (`.b64 s[8]`, читаемый как i32), — то есть
  ведёт к записи за границу.

### Дифференциальный фазер MLIR-контура

Тот же сгенерированный PTX-ядро идёт двумя НЕЗАВИСИМЫМИ путями:

* наш текстовый интерпретатор PTX — эталон семантики;
* наш MLIR-контур: фронтенд -> диалект `rouge` -> петли -> LLVM IR ->
  бинарник -> исполнение на CPU.

Результаты обязаны совпасть **поэлементно** (сумма скрыла бы перестановку).
40 итераций по 23 операциям (включая `prmt`, `bfi`, `bfe`) — расхождений нет.

Фазер нашёл баг сразу: знаковое расширение байтов в `dp4a` всегда было
беззнаковым. Эталон был прав. Второй улов — `prmt` во фронтенде: выбранный
байт не маскировался до 8 бит, и старшие байты `a` протекали в соседние
выходные байты. При `a = 0x3039` и селекторе `0xf003` правильный ответ
`0x00393900`, а фронтенд давал `0x30393900`. Трёхсторонний тест на
`bitfield.ptx` этого не видел (там `a` и `b` подобраны под сравнение с ISA),
а случайный фазер увидел на первом же прогоне: поэтому нужны оба.

Ячейки CI: `compiler_mlir_fuzz` (генерация) и `compiler_mlir_fuzz_cases`
(повтор сохранённых провалов). Провал сохраняется в `tests/fuzz/cases/`
вместе с входом, и `--replay` прогоняет его заново: тот же текст ядра, тот
же вход, то же сравнение. Это регрессионный тест, а не пример вывода —
падение там означает, что вернулось ровно то, что чинили.

Второй шаблон генератора — `--template phases`: общая память, барьер и две
фазы, причём вторая фаза читает **чужой** элемент (`n-1-tid`). Индекс
намеренно не «поток + константа», так что векторизатор здесь ни при чём:
проверяется семантика фаз и общей памяти (и то, что проход оставляет такой
индекс скалярным). Ячейка CI: `compiler_mlir_fuzz_phases`.

Третий шаблон — `--template demoted`: та же форма, что `phases`, но общая
память адресуется так, как её реально эмитит nvcc — 32-битный базис
`mov.u32 %r, <shared symbol>`, цепочки `add.s32` и доступы `[reg+imm]`, без
`cvta.shared.u64` и `add.s64`. Проверяет восстановление демотированной
адресной арифметики фронтендом (32-битный базис, накопление нескольких
смещений, константное байтовое смещение). Ячейка CI: `compiler_mlir_fuzz_demoted`.

Четвёртый шаблон — `--template atomic`: общий счётчик, который все потоки
увеличивают атомарно (`atom.add.u32`), и чтение результата после барьера.
Сумма **не зависит** от порядка атомарных операций, поэтому результат
детерминирован — это проверка атомарности, а не расписания. Шаблон нашёл
настоящий баг прохода `rouge-to-scf`: чтение памяти, не зависящее от thread
id, выносилось из фазы наружу и потому читало память **до** записи другой
фазой (молчаливо неверный ответ, а не падение). Теперь доступ к памяти
остаётся в своей фазе; выносятся только чтение параметра и аллокация.
Ячейки CI: `compiler_mlir_fuzz_atomic`, `compiler_ptx_fuzz_atomic`.

Пятый шаблон — `--template loop`: счётный цикл (обратная ветка `bra $L` с
условием выхода `@%p1 bra $L_done`). Фронтенд переводит цикл в `scf.while` с
переносом индуктивной переменной и накопителя, а проход `rouge-to-scf`
понижает цикл **внутри** цикла по потокам: thread id приходится
переназначать внутри области цикла, иначе клон повисает на старом ядре.
Проверено побитово: интерпретатор и MLIR дают одинаковый результат.
Ячейки CI: `compiler_mlir_fuzz_loop`, `compiler_ptx_fuzz_loop`.

Шестой шаблон — `--template dowhile`: тот же цикл, но с условием **внизу**
тела и предикатанной обратной веткой (`@%p1 bra $L`) — форма, которую
эмитит nvcc. Условие `scf.while` строится из переносимых значений цикла
(счётчика), а не из значений на входе в цикл, поэтому do-while (тело
выполняется хотя бы один раз) совпадает с формой nvcc.
Ячейки CI: `compiler_mlir_fuzz_dowhile`, `compiler_ptx_fuzz_dowhile`.

### Модель расхождений: маска вместо сериализации

Расхождение внутри тела потока раньше **сериализовалось**: потоки шли по
очереди, каждый по своей ветке. Это корректно (без барьера порядок между
потоками на GPU всё равно не определён), но векторный юнит простаивает.

Теперь ветвление становится **маской**. В векторной форме:

```
%lane = arith.addi %splat, %step          // [iv, iv+1, iv+2, iv+3]
%mask = arith.cmpi slt, %lane, %bound     // vector<4xi1> — кто активен
vector.maskedstore %dst[%iv], %mask, %v    // неактивные полосы не пишут
```

Условие вычисляется **по полосам** (идентификаторы полос — это
`vector.step` + broadcast от индуктивной переменной векторного цикла), так
что маска говорит, какие полосы активны. Обращения внутри региона становятся
маскируемыми (`vector.maskedload` / `vector.maskedstore`), а арифметика едет
как есть — она поэлементная.

Хвост (последние V-1 итераций) остаётся скалярным, с веткой: это максимум
три итерации, сериализация тут ничего не стоит.

Проверки: структурная (`mlir_divergence_mask` — в результате есть
`vector.maskedstore`) и **СЕМАНТИЧЕСКАЯ** (`mlir_divergence_mask_semantics` —
скалярная и векторная сборки обязаны посчитать одно и то же: первая половина
скопирована, вторая нет).

Что пока не поддержано: условие расхождения — только сравнение
идентификатора потока (или его плюс константа) с константой; у региона нет
результатов; вложенных расхождений нет.

### Апстримного `gpu-to-scf` НЕ существует

Проверено по исходникам LLVM 23.1.4 (каталог `mlir/lib/Conversion/GPUCommon/`,
полная история `llvm-project`): прохода `convert-gpu-ops-to-scf` и файла
`GPUToSCF.cpp` нет ни в LLVM 23, ни в 19–22, ни в 6–18, ни в отдельном
репозитории `llvm/mlir`. По всей истории проекта конверсии в SCF — это
`ArmSMEToSCF`, `ControlFlowToSCF`, `OpenACCToSCF`, `SCFToControlFlow`,
`SCFToEmitC`, `SCFToGPU` (обратное направление), `SCFToSPIRV`, `TosaToSCF`,
`VectorToSCF`. Понятия «фазы» в MLIR тоже нет.

То есть наш проход — не перенос существующего, а собственная разработка. Это
важно для честности: сравнивать не с чем, и любые утверждения «как в MLIR»
нужно проверять по спецификации, а не по чужому коду.

Что из апстрима всё же стоит знать (проверено):

* каноническое отображение измерений (из `GlobalIdRewriter.cpp`):
  `global_id.x = thread_id.x + block_id.x * block_dim.x`; значит внешний цикл —
  по сетке (`grid_dim`), внутренний — по блоку (`block_dim`), а thread id
  становится индуктивной переменной внутреннего цикла (так и сделано у нас);
* `gpu.barrier` по контракту запрещает расхождение: нельзя, чтобы две группы
  потоков пришли к разным барьерам. Значит разбиение тела на фазы по
  барьерам — не изобретение, а требование семантики;
* политика апстрима при расхождении — **отказаться** (в `SCFToGPU.cpp` это
  `return failure()`), а не сериализовать. Наш проход поступает так же;
* `scf.for` не является `IsolatedFromAbove` — тело может ссылаться на внешние
  значения; ограничение — это доминирование, и ошибка «operand does not
  dominate this use» приходит из другого места;
* `Operation::clone` использует `lookupOrDefault` — НЕотображённый операнд
  молча становится ссылкой на старую функцию. Отсюда и наша грабля с
  висящими значениями: маппить надо явно, и `getUsedValuesDefinedAbove` —
  канонический способ собрать внешние значения.

### Векторизация unit-stride доступов: проход работает, семантика проверена

`--rouge-unit-stride-to-vector` превращает цикл потоков в векторный цикл (V
элементов за итерацию) плюс точный скалярный хвост. Проверок две:

* **структурная** (`mlir_unit_stride_to_vector`): в результате есть
  `vector.load`/`vector.store` и скалярный хвост;
* **СЕМАНТИЧЕСКАЯ** (`mlir_unit_stride_to_vector_semantics`): один и тот же модуль
  запускается дважды через штатную цепочку MLIR → LLVM IR → бинарник — как есть и
  после прохода — и напечатанные значения должны совпасть. Это единственная
  проверка, которая говорит, что векторизация не «просто сработала», а считает
  то же самое.

Проход устроен в две фазы, и это не stylistic choice: **все проверки — до
изменений**. Раньше проход сначала переписывал, а потом проверял; отказ
оставлял модуль наполовину переписанным, и падал уже верификатор, а не проход.

Отдельно про общую память: адресное пространство живёт в ТИПЕ memref, и
объявленная внутри ядра общая память (`memref.alloc() : memref<64xf32, 3>` —
ровно как `.shared` в CUDA) превращается в **private-накопитель на блок**: ядро
вызывается один раз на блок, значит и накопитель — на блок. `dealloc` общей
памяти удаляется: память умирает вместе с блоком, а оставленный `dealloc`
выполнялся бы по разу на поток (фазы — это циклы по потокам), то есть двойное
освобождение. Общая память, приходящая **параметром**, по-прежнему отвергается
громко: копия на блок должна жить у вызывающего, а запуск не знает размера.

По дороге вскрылись два бага, общих для обоих диалектов (lowering один и тот
же):

* **значение, определённое в одной фазе и использованное в другой**: фазы —
  это РАЗНЫЕ циклы, значение между ними не выживает, а клон поздней фазы
  ссылался на операцию старого ядра, которое стирается в конце, — висячая
  ссылка, падавшая в верификаторе сильно позже. Операции идентичности
  (thread id, block id) теперь маппится в КАЖДОЙ фазе (поздняя фаза может
  использовать thread id, определённый в ранней), а **чистая функция от
  thread id** (`index_cast(tid)`, `tid*4`) перевычисляется в каждой фазе,
  которой она нужна. Значение, зависящее от **памяти** (`index_cast` от
  загрузки) и пересекающее границу фаз, по-прежнему отвергается громко: его
  перевычисление прочитало бы память в другой момент. Без этого правила
  отвергались бы почти все настоящие ядра: nvcc считает индекс потока один
  раз и использует его во всех фазах.
* **пересборка `memref.alloc` с другим типом через ODS-билдер даёт операцию с
  неправильным `operandSegmentSizes`**, и верификатор падает на ней. Смена типа
  результата на месте сохраняет атрибуты и использования.

Что проход отвергает (громко): шаг не 1; нижняя граница не кратна ширине
вектора; memref не 1-D/статический/не с кратным смещением/не с шагом 1
(`vector.load` требует единичного шага последнего измерения, иначе операция не
проходит верификацию MLIR); индекс обращения не «поток + константа»; значение
пришло **извне тела** (скаляр снаружи в вектор не положить) или **пересекает
границу расхождения** (значение, посчитанное под маской, валидно только под
ней: остальные полосы держат pass-through, а не результат); операция не из
`arith`/`math` (у остальных нет поэлементной замены скалярного типа на
векторный, и угадывать её — значит тихо считать не то); результат
поэлементной операции не поэлементного типа.

Цепочка поэлементных операций (`index_cast` -> `extui` -> арифметика)
векторизуется как есть: тип результата клона берётся из **исходного** типа
результата, а не из типа первого операнда — иначе `index -> i32 -> i64`
превращался бы в вектор не того типа (на этом проход и спотыкался).

Отдельно про выравнивание: у `vector.load`/`vector.store` есть атрибут
`alignment` (с LLVM 21). **Без него** lowering в LLVM считает выравнивание по
ЭЛЕМЕНТУ (4 байта для f32), а не по вектору (16 байт для `vector<4xf32>`) —
и обращение может быть выровнено по 16 байтам на указателе с выравниванием 4.
Наш проход выставляет атрибут явно.

Ещё одна грабля, общая для проходов: **диалекты, чьи операции создаёт проход,
надо объявлять в `getDependentDialects`**, а не грузить внутри прохода. Проход
над `func.func` выполняется MLIR-ом **параллельно** по функциям, и загрузка
диалекта из нескольких потоков — гонка (она и падала: SEGV в
`getOrLoadDialect`).

Остаток работы по этому рубежу: довести фронтенд до настоящих ядер nvcc
(циклы, 32-битные адреса общей памяти, `prmt`/`bfi`/`bfe`, атомики) и
расширять фазер на барьеры, атомики и общую память.

Честная граница нынешнего фронтенда: настоящее ядро nvcc (наш
int8-GEMM) он **отвергает** — там циклы и 32-битные адреса общей памяти.
Отказ здесь — правильный ответ, а не «почти работает».

### Бэкенд — плагин, а не кодогенератор: `rouge-compile`

Своей кодогенерации у контура нет и не планируется: после диалекта всё едет
по стандартным диалектам в LLVM IR, а машинный код делает бэкенд LLVM.
`mlir/tools/rouge-compile/rouge-compile` — «плагин», который собирает цепочку
под цель:

```
PTX --rouge-ptx2mlir--> rouge --rouge-to-scf--> петли
    --rouge-unit-stride-to-vector--> векторный цикл (+ скалярный хвост)
    --canonicalize --cse-->         (пустой хвост и мёртвые значения — прочь)
    --mlir-opt-->                   стандартные конверсии в LLVM dialect
    --mlir-translate-->             LLVM IR
    --llc-->                        машина

В сторону NVPTX (та же команда, `--target nvptx`):
PTX --rouge-ptx2mlir--> rouge --rouge-to-gpu--> gpu
    --convert-gpu-to-nvvm--> LLVM dialect + NVVM (thread id, barrier)
    --rouge-extract-kernels--> только device-часть (.ptx без хоста)
    --mlir-translate--> LLVM IR --clang (NVPTX)--> .ptx
```

Цели: `cpu` (`x86_64-unknown-linux-gnu`), `rvv`
(`riscv64-unknown-linux-gnu -mattr=+v,+m,+a,+f,+d,+c`) и `nvptx`
(`--sm sm_75|sm_80|...`, по умолчанию `sm_80`). Флаги: `--grid`,
`--block`, `--shape I=<n>x<тип>`, `--emit-llvm` (остановиться на LLVM IR),
`--keep-mlir` (сохранить промежуточные файлы), `--target`, `--sm`.

**PTX ABI в NVPTX-цели.** Конверсия `gpu -> LLVM` идёт с
`use-bare-ptr-memref-call-conv`: memref-аргументы ядра становятся обычными
указателями (`.param .u64 .ptr .global`), а не 40-байтными дескрипторами
memref. Поэтому один и тот же раннер (`gpu_exec_rungpu`, `fuzz_run_gpu`)
грузит и .ptx от `ptx2ir`, и .ptx от контура. Обратная сторона: у
bare-pointer ABI нет места для размеров, поэтому **memref обязан иметь
статическую форму** — отсюда `--shape` у `--target nvptx`.

**Общая память в NVPTX-цели.** `memref.alloc` в адресном пространстве 3
опускается не в `malloc` (устройство его не вызывает — это была первая
ошибка при запуске фазера на карте), а в `memref.global` в том же
пространстве внутри `gpu.module`: LLVM-lowering делает из него
`llvm.mlir.global addrspace(3)`, NVPTX-бэкенд — статический `.shared`
массив на блок. Динамическая общая память (workgroup attribution) не
подходит: раннер запускает ядро с нулевым dynamic shared memory.

Замер на `test/vector_copy.ptx` (ядро копирования, индекс = thread id):

* `--target rvv` -> `vle32.v v8, (a4)` / `vse32.v v8, (a4)` — настоящие
  векторные обращения RVV;
* `--target cpu` -> `movaps (%rax,%rcx,4), %xmm0` / `movaps %xmm0, ...`.

Отдельного прохода `vector-to-rvv` не понадобилось: `vector.load`/`store`
опускаются в `llvm.load <4 x float>`, а выбор RVV-инструкций — работа
бэкенда LLVM (ровно то, ради чего бэкенды и вынесены в плагины).

Ячейки CI: `mlir_rouge_compile_rvv` и `mlir_rouge_compile_cpu` (структурные:
в ассемблере обязаны быть векторные обращения). Семантику той же цепочки
проверяет `mlir_rouge_to_rvv` — исполнение под `qemu-riscv64`.

**Выравнивание — предупреждение, а не мелочь.** Проход выставляет
`alignment` по вектору, значит базовый указатель memref обязан быть выровнен
на ширину вектора (16 байт для `vector<4xf32>`); проход проверяет смещение
memref, но не может проверить указатель, который дал вызывающий. Для
`memref.alloc` внутри MLIR это выполняется, для внешнего указателя — это
контракт вызывающего.

**Что дала NVPTX-цель.** Третий путь исполнения сразу нашёл расхождение,
которого не видели два согласных: `shl`/`shr` при смещении больше ширины
регистра. PTX ISA 9.7.9.8/9.7.9.9 говорит «shift amounts greater than the
register width N are clamped to N», а интерпретатор и AOT-эмиттер оба брали
смещение по модулю N — и совпадали друг с другом на неверном ответе
(`shl.b32 1, 33` давало 2 вместо 0). Теперь clamp реализован во всех трёх
путях, а границы закреплены ядром `tests/kernels/shift_clamp.ptx`: оно
исполняется и AOT-ячейкой (`compiler_nvptx_gpu_exec`), и контуром
(`mlir_rouge_nvptx_shift_clamp`), ожидаемые значения выведены из текста ISA.

Чего ещё нет (следующие итерации, по порядку):

1. **Структура CFG**: ветки внутри тела цикла (`@%p bra` к точке слияния
   внутри цикла) и значения, определённые в охраняемом блоке и
   используемые после него (`scf.if` с результатами). Без этого настоящие
   ядра nvcc (`int8_gemm`) не проходят — нужен структурайзер, а не заплатка.
2. **Warp-операции и тензорные ядра** (`shfl`, `vote`, `mma`, `ldmatrix`):
   фронтенд их пока не понимает и отказывает громко.
3. Атомики `atom.cas` (нужен `cmpxchg`) и `red` с плавающей точкой в
   NVPTX-цели: в диалекте они уже есть, но на карте через контур ещё не
   проверялись.

## Сборка

Нужен LLVM с MLIR (в дереве LLVM или готовый пакет):

```sh
cmake -S . -B build -DROUGE_ENABLE_MLIR=ON -DMLIR_DIR=/path/to/llvm/lib/cmake/mlir
cmake --build build
ctest --test-dir build
```

Проверенная конфигурация (без root, только распакованный релиз LLVM):

```sh
curl -L -o llvm.tar.zst https://github.com/llvm/llvm-project/releases/download/llvmorg-23.1.3/LLVM-23.1.3-Linux-X64.tar.zst
zstd -dc --long=30 llvm.tar.zst | bsdtar -xf - -C ~/.local/llvm-mlir --strip-components 1
cmake -S software/rouge-compiler -B build-mlir -DROUGE_ENABLE_MLIR=ON \
      -DMLIR_DIR=$HOME/.local/llvm-mlir/lib/cmake/mlir
cmake --build build-mlir
ctest --test-dir build-mlir -R mlir
```

Две детали, на которые стоит смотреть: `--long=30` у `zstd` (фрейм требует
окно в 1 ГБ) и подстановка `zstd::libzstd_static` на shared-вариант, если
статической zstd в системе нет (LLVM в своих CMake-экспортах на неё
ссылается).

Без MLIR проходы не собираются: таргет выключен по умолчанию, `ctest`
просто не содержит MLIR-тестов. Это осознанно — стадия 1 (ptx2ir) не должна
требовать MLIR, чтобы проверяться на любой машине с clang.

## Почему так

Сырой PTX — это SIMT: один поток = один элемент, ветвления по `tid`.
RVV — это data-parallel: один поток = вектор. Прямой транслятор будет
«наивным и медленным» (одна инструкция на элемент). Правильный путь —
**сначала измерить** форму обращений к памяти (проход выше), потом сливать
соседние обращения в векторные операции, и только потом отображать их в RVV.
Отсюда порядок: анализ → GPU→SCF → unit-stride→vector → vector→RVV.
