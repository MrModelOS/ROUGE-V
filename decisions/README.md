# Реестр архитектурных решений (ADR)

> `decisions/README.md` — правила ведения реестра.
> Формат: [Michael Nygard, ADR](https://github.com/joelparkerhenderson/architecture-decision-record) (адаптировано).

## Зачем

Каждое серьёзное решение проекта фиксируется: **контекст → варианты → решение → последствия**. Это позволяет:
- двигаться по плану и не переспоривать одно и то же месяцами;
- новичку за 15 минут понять, почему стек устроен так, а не иначе;
- пересматривать решения осознанно (пересмотр = новая запись, старая остаётся историей).

## Процесс

1. Решение, которое влияет на > 1 подсистему, на расходы > $100k, или меняет публичную стратегию — **обязательно ADR**.
2. Черновик: файл `decisions/NNNN-короткое-название.md` по шаблону ниже.
3. Обсуждение в команде (минимум: владелец + скептик).
4. Итог: статус `Принято (date)`. Отклонённые варианты остаются в файле.
5. Отмена решения: новый ADR с полем «Отменяет: NNNN».

## Шаблон

```markdown
# ADR-NNNN: <Заголовок>

- **Статус:** Принято / Предложено / Отклонено / Заменено
- **Дата:** YYYY-MM-DD
- **Владелец:** <имя/роль>
- **Отменяет/изменяет:** <NNNN если есть>

## Контекст
Почему решение вообще возникло. Какие факты и ограничения.

## Варианты
1. <вариант А> — плюсы/минусы
2. <вариант Б>

## Решение
<что выбрали и почему, ссылки на документы>

## Последствия
<что это означает: для софта, для кремния, для денег, для рисков>

## Обратные сигналы (когда пересматривать)
<какие события должны заставить пересмотреть решение>
```
